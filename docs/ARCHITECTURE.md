# Architecture — Système Moulins Ehl Taya (`the_rock_web`)

React + Vite rewrite of the `the_rock` front-end (Next.js). Bilingual: **Arabic (default, RTL)** and
**French (LTR)**. Talks to the Django backend (`tayea_mills`) through `/api` on its own origin.

> Status: login, app shell, **Shipments**, **Milling** (on the real grinding API), **Refining**,
> **Clients**, **Final settlements**, **Inventory**, **Users** and **Settings** are built and
> connected to the API. The other sections (dashboard, accounting, …) render an empty page, as in
> `the_rock`.

`/` and `/:locale` redirect to the login page. Invalid ids in the URL answer "not found".

**Signed-in layout:** its loader (`loadSignedInUser`) sends a visitor without a valid session to
login and reads `/auth/me/` for the top-bar name, the role name and the access (`accessFromApi`).
A user is sent away from a section they cannot open (`canOpen`) to their home (`homeHref`): the first of
dashboard, shipments, milling, refining, inventory, customers, users they can open, else settings.

**Access model:** roles are created in the app (Users → Roles and permissions), each with a free name,
"limited to one project" (`is_project_scoped`, its users need a project) and view / add / edit /
delete rights per module: shipments, grinding (Milling), refining, inventory, customers, accounts
(Users), locations (Settings → projects). Any right on a module gives its view right; approve
follows edit. A section opens when the role can view its module; settings home, profile and
language are open to everyone; sections still to build (dashboard, accounting…) need view on every
module. Final settlements have their own module, `settlements` (view / add / edit / delete in the roles
screen, "Final settlement"); the section, its pages and buttons follow it, never the shipments rights. Form pages (new shipment, new settlement, new / edit project, new /
edit machine) need the add or edit right.
Superusers open everything. The backend enforces the rights; the UI only hides. Users get a role,
not rights of their own.

**View-only roles:** viewing a section also lets the backend serve the records its pages show from
other modules (projects and machines, the grindings on Refining, the shipments on Milling, the
refinings on Inventory, the clients on Shipments). The signed-in layout puts the user's `Access` in
`AccessContext` (`lib/accessContext.ts`); screens ask `useCan()(module, right)` and hide every add,
edit, delete and start button, and the drawer they open, that the role lacks. Inventory increase /
decrease need the add right (they are POSTs). Ending a grinding opens the
refining form only for a role that may add refinings and only when its mercury was added; otherwise
the drawer closes and the machine page reloads.

**Error page:** a page whose data fails to load shows `PageError` (in `PageStates.tsx`) inside the shell:
"not found" for a 404 (bad id, or an endpoint the backend does not have), "no permission" for a
403, "connection impossible, check your connection and try again" for a 502 / 503 / 504 (no code
shown), otherwise "something went wrong", with the HTTP error code shown, with "try again" (reloads the data) and "back to home". The same page covers a failure of
the signed-in layout itself. Inventory loads its lists with `tryLoad` (`lib/api/client.ts`): a refused or
failed list shows `PanelError` (reason + code) inside its panel, and the page keeps its title and
"new" button. Refining never does: without the refinings it cannot tell which grindings are already
refined, so a failed refinings list shows the error page (no figures, no queue, no new or edit form)
until "try again" loads it. When an error page appears it drops any pending message
(`useDismissToast`).

**Lost connection:** every request through `apiClient` (and login / token renewal in `api/auth.ts`)
goes through `connectedFetch`: it fails at once while the browser is offline and otherwise stops after
15 seconds. When the signed-in layout cannot reach the server, it shows the connection error page
instead of sending the user to login, so a reload while offline keeps the session. A request that fails or times out never throws: the
client answers it with a 503, so a page shows the connection error above instead of loading
forever, and `ConnectionBanner` shows the red bar until the next answer from the server or the
browser is back online. When the connection comes back, `AppShell` reloads the page's data
(`useRevalidateOnReconnect`).

**Save outcome (`saveOutcome`):** a 400 puts the backend's messages on the fields the form maps;
any other message of a 4xx (`non_field_errors`, `detail`, a field the form does not show) is shown in
the backend's own words above the buttons (`SaveFailureMessage`); a 5xx never shows its body, only
"save failed". These are definite refusals: the user can correct and save again. A 502 / 503 / 504,
a timeout or a lost connection is an **unknown outcome** (`unknown: true`): the request may have been
saved. The form says so (`common.saveUnknown`), hides its save button and ignores Enter
(`DrawerActions locked`, `useSaveFailure`), so the user can only close it and check the list (reloaded
on reconnect) before trying again. This does not prevent duplicates: the backend has no idempotency
key, so a user who opens the form again and saves can still create the same record twice.

**Reload after a refusal:** after a definite refusal (not an unknown outcome) `useSaveFailure`
reloads the page's data (`revalidate`, which reruns the page's loaders; there is no narrower
refresh), keeping what was typed and the backend's message, and never sends the save again. If the
reloaded data no longer has the record the form was for (another user refined, ended or deleted it),
its drawer closes and a red message says the data changed (`common.recordChanged`, 4 seconds). If the
reload fails, the error page shows instead.

**Page skeleton:** while the data of another page is loading, the shell shows a skeleton shaped
like that page (`skeletonShapeFor(pathname, projectScoped)`: `form`, `table`, `detail` or `cards`;
for a role limited to one project, `is_project_scoped` from `/auth/me/`, Shipments, Settlements,
Grinding and Refining draw the `table` of the project page they redirect to) and replaces it
in the same render as the backend's answer. It never shows when only the query changes (search,
page, drawer). The first load of the app shows the same skeleton.

(number `STL-<year>-<seq>`) of one customer's shipments in one project, with what the user enters:
grinding cost per bag (× the settlement's bags, `grinding_cost_per_bag`), refining cost per gram (charged on the shipments' gold without

optional (empty is 0, never negative). The backend works out the `totals` from the shipments
(bag transport and passenger transport at their full cost, payments not counted; the shipments'
debts; gold in grams, shown but not charged) and the final amount due = transport + shipments'
debts + bags × grinding cost per bag + gold × refining cost per gram + extra debt; the app only shows them.

from a finished shipment's "settle", the customer is shown read-only with no search), then the
project when the customer's unsettled shipments are in more than one (`?customer=&project=` in the
URL), and lists only that project's shipments of the customer that are `completed` (every bag ground
and refined) and that no settlement holds yet (`settleableShipments`, from `GET /settlements/?customer=`),
all ticked; at least one must stay ticked. A shipment still in grinding or refining is never offered
(the backend itself accepts any status when the shipments are given). Saving `POST`s the customer, the shipment ids and the amounts, then opens the
settlement's page; the backend's refusals (already settled, another project) show under the
shipments. The page shows customer and phone, project, shipments, who made it and when, the PDF in
Arabic or French (`GET /settlements/{id}/pdf/?format=pdf&lang=`, saved under its number), every
total and the final amount due; "edit the amounts" (shipments edit right) changes only the amounts
(`PATCH`, the customer and shipments stay); "delete" (shipments delete right) frees its shipments
for another settlement.

**Dates follow the events:** the new shipment's arrival, a grinding's start (start and edit
forms), its end and a refining's date are never typed: each form shows the date and time it was
opened read-only (`ReadOnlyDateAndTime`) and saves exactly that; an edit shows the recorded
arrival or start read-only. A grinding cannot start before its shipment arrived
(`startBeforeArrival`, from `OperationShipment.arrivedAt`) nor end before it started

**Number inputs:** every number field starts empty (no `0` or other pre-filled value); the user types it, `0` included. They have no up / down arrows (`app.css` hides the browser's spin buttons), and the value changes only by typing: `TextField` lets go of the field on a mouse-wheel turn (the page scrolls instead) and ignores the ↑ / ↓ keys. The new-machine form only hints the next free number.

**Inventory resources (`/api/v1/resources/`, `/resource-history/`):** per-project materials

`POST …/{id}/increase/` and `…/decrease/` (a quantity and a note only, never a shipment or a

shown as "Initial quantity". It also refuses a second mercury, water or fuel in a project under any

name: only the app limits a project to those three.

## 7. Backend connection

- **Development:** `npm run dev` (port 3000, fails if busy) forwards `/api` to `BACKEND_API_URL`
  from `.env` (default `http://127.0.0.1:8000`). `npm run preview` does the same for the build.
- **Production:** serve `dist/` as static files with every unknown path falling back to
  `index.html`, and forward `/api` to the backend from the same web server. No CORS is needed.
- **VPS with Docker (same server as the backend, domain with HTTPS):** our Caddy is the only server on
  ports 80 / 443 (the backend's production compose publishes nothing) and serves two sites:
  `DOMAIN` (`soukhour.net`, the app) and `API_DOMAIN` (`api.soukhour.net`, the API for other
  clients). Both forward to the backend at `BACKEND_URL` (`tayea-mills-web:8000`) over the backend's
  Docker network `BACKEND_NETWORK` (`tayea-mills-api`, created by the backend's
  `docker-compose.prod.yml`). The app keeps calling `/api` on its own origin (no CORS); Caddy
  forwards those calls with `Host: API_DOMAIN`, the only host the backend's `ALLOWED_HOSTS` needs.
  1. DNS `A` records for `soukhour.net` and `api.soukhour.net` → the VPS; ports 80 and 443 open.
  2. Start the backend first (`docker compose -f docker-compose.prod.yml up -d --build`, then
     `docker compose -f docker-compose.prod.yml exec web python manage.py migrate`): it creates
     the `tayea-mills-api` network.
  3. In this repository on the VPS: `cp .env.example .env` (the values are the production ones).
  4. `docker compose up -d --build`. Caddy gets and renews both certificates by itself (kept in the
     `caddy_data` volume), serves `dist/` with every unknown path falling back to `index.html`,
     caches `/assets/` for a year (a missing asset answers 404, never the page) and never caches
     `index.html`.
  5. To deploy a new version: `git pull && docker compose up -d --build`.
